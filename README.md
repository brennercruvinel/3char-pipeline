# 3char-pipeline

Build pipeline for the [3char](https://huggingface.co/datasets/brennercruvinel/3char) dataset. It contains 64 parsers that read code systems, symbol sets and vocabularies from documented reference sources and write one Parquet file per system in a common schema, together with the checks that must pass before an upload. The repository holds code and provenance records only: raw sources and Parquet files are not committed.

The dataset card on the Hub describes the data itself. This README covers how the data is built, checked and extended.

## Requirements

Python 3.11 or later, [uv](https://docs.astral.sh/uv/), network access to the URLs in `systems.tsv`, and about 2 GB of disk space for the raw sources.

```bash
uv venv .venv && uv pip install --python .venv/bin/python -r pipeline/requirements.txt
```

## Building the dataset

```bash
.venv/bin/python pipeline/download.py     # fetch every raw source and verify its SHA-256 against CHECKSUMS.tsv
.venv/bin/python pipeline/build.py        # run the 64 parsers; one Parquet file per system under data/<domain>/<id>/
.venv/bin/python pipeline/validate.py     # test every code against its system's code_pattern; non-zero exit on any mismatch
.venv/bin/python pipeline/build_hub.py    # select the publishable systems and write hub/ (Parquet, systems.parquet, CHANGELOG.md)
.venv/bin/python pipeline/build_card.py   # write hub/README.md: YAML and systems tables from systems.parquet, prose from pipeline/card_body.md
```

`download.py` exits with an error when a file's SHA-256 differs from the value in `CHECKSUMS.tsv`. An upstream change is adopted deliberately with `--accept-new`, which rewrites the manifest entry, and is then recorded in `CHANGELOG.md`. `validate.py` accepts no mismatches other than those listed in `pipeline/known_exceptions.py`, each with its reason.

The dataset card is generated, never edited by hand: changes to its text go in `pipeline/card_body.md`. Setting `CH3_HUB_DIR` points `build_card.py` at a hub folder other than `hub/`, such as a local clone of the Hub repository.

## Layout

```
data/<domain>/<id>/raw/<file>      raw source as fetched; never rewritten, never committed
data/<domain>/<id>/<id>.parquet    parser output; schema in SCHEMA.md
hub/                               the upload: data/<domain>/<id>.parquet for publishable systems, systems.parquet, README.md, CHANGELOG.md
```

`systems.tsv` has one row per system (64 rows, 15 columns, documented in `SCHEMA.md`). It is generated by `build_systems.py` from the retrieval URLs in `history/SOURCES.tsv`, the curated metadata in `pipeline/systems_meta.py` and the raw files on disk. `systems.parquet` in `hub/` is the same table restricted to the published systems.

## Provenance

For each system, `systems.tsv` records the assigning authority and, separately, the URL the file was fetched from. The two often differ, and the difference is part of the provenance. `CHECKSUMS.tsv` records the SHA-256 and size of every raw file. `versions.py` reads the version string that a source publishes from the file itself, so the recorded version cannot drift from the file on disk. `retrieved_at` is the fetch date.

`LICENSES.md` records the license triage of all 64 sources against each authority's own terms, with verbatim quotes. Systems whose authority forbids redistribution are parsed but never written to `hub/`. `history/SOURCES.tsv` is the source table the project started from; `build_systems.py` still reads its URLs.

## Validation

Two checks can be reproduced from this repository:

- `validate.py` tests that every emitted code matches its system's anchored regular expression. `pattern_status` in `systems.tsv` records whether the expression was written against the real file (`derived`) or is still loose (`provisional`). All 58 published systems are `derived`.
- `crosscheck_wikidata.py` tests every published code, as a full match, against the Wikidata format constraint (P1793) of the corresponding property, for the 13 systems that have one. The constraint table is in `external/`, with its retrieval date in the file name. The script documents the forms used for comparison: dotted ICD-10-CM codes, complete UN/LOCODEs, and BCP 47 language subtags only.

`census.py`, `keys.py`, `equivalences.py` and `manifest.py` produce the statistics, the identification keys, the links between lists that describe the same entities (with the card's figure) and the deposit manifest; their outputs are in `deposit/`. `card_check.py` compares every number in the card with those outputs and exits with an error on any difference:

```bash
.venv/bin/python pipeline/equivalences.py hub deposit/equivalences.json hub/figures/equivalences.svg
.venv/bin/python pipeline/card_check.py hub/README.md deposit/census.json deposit/keys.json deposit/crosscheck_wikidata.json deposit/equivalences.json
```

## Writing a parser

```python
from core import parser, row, read_csv

@parser("cmp/sts")
def http_status(path, sysrow):
    for r in read_csv(path):
        yield row("cmp/sts", r["Value"], r["Description"], extra={"reference": r.get("Reference")})
```

Register one function per system ID and yield canonical rows. Then add the system to `systems_meta.py` with its authority, URL, license and a regular expression written against the file, and run `validate.py`. A code that fails the expression is treated as a parser or pattern bug until it is shown to be a malformed row in the source; in that case it goes in `known_exceptions.py` with the reason.

## Contributing

Issues and pull requests are welcome. A pull request that adds or changes a system should include the `systems_meta.py` entry, the parser, the `CHECKSUMS.tsv` line, the `LICENSES.md` row with the quoted terms, and a `CHANGELOG.md` entry. The build must pass `validate.py`.
